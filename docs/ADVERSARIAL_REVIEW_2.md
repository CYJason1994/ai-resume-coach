## 二、🔴 仍存的硬伤（M0 前必须解决）

### R2-C1. 岗位种子"数据从哪来、版权归谁"仍未回答
- **问题**：v0.2 说 M1 强制交付 200–500 个角色 + 脚本灌库，但没说数据来源。手写 200–500 份高质量岗位 JSON 是**以周计**的真实工作量；爬招聘网站违反 ToS；直接搬运 O*NET/BOSS 等数据集有授权风险。
- **影响**：M1 会因"没数据"卡死，或被迫用侵权/低质数据，埋法律与质量雷。
- **修复（必须给可落地方案）**：
  ① 首期**手工编写 ~80–120 个高频岗位**（覆盖主流职能：前端/后端/数据/产品/运营/测试/设计等），每个含 `required_skills`/`level`/`responsibilities`；明确这是"种子 v1"，后续人工扩充。
  ② 若引入外部数据集，**只采用明确可商用/CC 协议**的来源，并在 `jobs.source` 标注出处与许可。
  ③ 提供 `scripts/seed_jobs.py` + `data/jobs/*.json` 的清晰结构，让后续扩充是"填表"而非"重写"。
  ④ 在计划里写明**数据规模里程碑**：v1=80–120 手写 → v2=扩充至 300+ → 运营期持续。

### R2-C2. 匿名 MVP 的文件访问控制只是"原则上"有
- **问题**：v0.2 加了 `access_token`/`result_token`，但没定义签发/校验的**具体契约**：token 如何生成（UUID? JWT?）、存哪、前端如何携带、后端每个读路径是否都校验、`task_id` 本身是否可猜测导致越权。
- **影响**：匿名上传意味着无账号体系，若 `task_id` 或 `storage_key` 可枚举，他人可批量拖走他人简历（PII 泄露）——这比"能否删除"更严重，是合规红线。
- **修复**：
  ① 上传即签发**高强度随机 `access_token`**（如 32+ 字节随机串），`resumes` 记录关联；任何读（结果/下载/状态）必须带该 token，服务端校验，否则 403。
  ② `task_id` 用不可猜测的 UUID；`storage_key` 同样随机，不直接暴露。
  ③ 明确"结果查看 URL"形如 `/r/{task_id}?token=...`，token 不进日志、不进前端状态可持久化但需用户主动保存。
  ④ 在 §7.1 写出完整的访问控制契约，而非一句话。

### R2-C3. 单点 LLM 的"韧性"仍停留在口号
- **问题**：v0.2 提了"降级模式（规则匹配）+ 重试退避"，但没定义：**何时算不可用**（错误率? 超时? 限流 429?）、退避参数、降级对用户的**可见提示**、以及 DeepSeek 速率限制未知下的预算护栏数字。
- **影响**：MVP 演示时一旦被 DeepSeek 限流（新账号额度常偏低），要么白屏要么静默失败，体验崩塌。
- **修复**：
  ① 定义不可用判定：连续 N 次 429/5xx/超时 → 进入降级，并设冷却恢复探测。
  ② 指数退避 + 抖动；队列积压时返回"处理中，预计 X 秒"，而非失败。
  ③ 降级必须**用户可见**：标注"AI 理由暂不可用，已用规则匹配"，并给出走通路径。
  ④ 给预算护栏数字（见 R2-M2）。

## 三、🟠 重要缺陷（决策未落地 / 会返工）

### R2-M1. ARQ vs BackgroundTasks 仍留口子
- v0.2 标题写"定为 ARQ"，但 §3/§8 仍出现"或 BackgroundTasks"。**必须二选一锁死**：建议 **M0 起即用 ARQ**（Redis-only、可重启持久、dev/prod 一致）；不用 BackgroundTasks（进程内、重启丢失、破坏环境一致性）。含糊会直接导致 M0/M1 返工。

### R2-M2. 成本护栏没有数字
- "全局信号量 + 预算线"是空话，没给数字。给粗略估算以便设护栏：
  - 嵌入：简历 ~3k tokens × $0.02/1M ≈ **$0.00006/份**；岗位 200–500 个一次性 ≈ 可忽略。
  - 结构化 chat：~5k tokens 出 ≈ 依 DeepSeek 定价（需查当前价，假设 ~$0.0001–0.0003/份）。
  - 匹配：Top-K 批量一次调用 ~若干 k tokens。
  - **建议**：设单份简历处理成本上限（如 $0.01 熔断）、日/月调用预算、并发信号量（如 4–8）。没有数字，限流=摆设。

### R2-M3. eval 仍虚（谁标、何时跑、什么指标）
- §7.7 说"~20–50 份黄金集"，但没说：谁来标（你？我？）、CI 何时跑（每次 PR? 每晚?）、指标阈值多少算回归。
- **修复**：M1 起在 CI 跑一份 **≥20 份**手工标注集；指标 = 字段级 F1（邮箱/电话/技能召回）、匹配 Top-1/Top-3 命中率、LLM-as-judge 一致性；设基线阈值，跌破即告警。先小后大，避免"永远标不完"。

### R2-M4. pgvector 启用与索引调参是易漏生产细节
- 启用 `pgvector` 扩展需 `CREATE EXTENSION`（托管库要确认支持）；HNSW 索引需先有数据量再调 `m`/`ef_construction`；ivfflat 需先 `VACUUM` + 设 `lists`。迁移顺序、扩展权限、首次建索引的锁表风险都要在 M0  migrations 里写明。

### R2-M5. "最小化上送"与"匹配质量"的边界未定
- §6 说剔除姓名/身份证/联系方式，但没定义**到底送哪些字段**。送太少 → 匹配退化（尤其行为/软实力判断）；送太多 → 合规风险。
- **修复**：明确定义上送 payload schema（如：技能列表、工作经历的"公司/职位/时长/职责摘要"、教育、目标职能；**剔除**姓名/性别/年龄/身份证/电话/邮箱/住址），并在 §7.3 落地为代码级白名单。

## 六、第二轮结论

v0.2 解决了首轮大部分关键项，质量明显提升。但**仍不能进 M0**，因为：

1. **R2-C1 岗位数据来源/版权**不解决 → M1 必卡死；
2. **R2-C2 匿名访问控制契约**不落地 → 有 PII 泄露红线风险；
3. **R2-C3 单点 LLM 韧性**不定义 → 演示易崩；
4. **R2-M1 ARQ 未锁死** → M0/M1 返工。

**建议动作**：先拍板 C1（数据来源方案）、C2（access_token 契约）、M1（ARQ 锁死）、M2（成本数字），把这些补进 v0.3，再启动 M0。其余 🟠🟡 可在 M0/M1 执行中边做边补，但 C1–C3 与 M1 是 blocker。
