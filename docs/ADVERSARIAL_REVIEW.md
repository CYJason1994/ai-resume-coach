## 一、审查结论（一句话）

整体方向正确（异步化拓扑、解析/理解分离、向量+LLM 双引擎匹配都成立），但原规划在 **模型版本、延迟预算、合规、OCR 权重、岗位冷启动** 五处有明确漏洞；其中「模型弃用」与「延迟预算自相矛盾」会在开发期就爆发，必须在进 M0 前修订。

## 二、先校正我自己（已用 Web 核实）

- ✅ **DeepSeek 提供 Embeddings API**：`POST /v1/embeddings`，模型 `deepseek-embedding`，**1536 维**，约 $0.02/1M tokens。→ 原方案「pgvector + DeepSeek 嵌入」路线成立，SQL 中 `vector(1536)` 也正确。撤销"DeepSeek 无嵌入"的疑虑。
- ⚠️ **但聊天模型正在改名**：`deepseek-chat` / `deepseek-reasoner` 将于 **2026-07-24 15:59 UTC 弃用**（距今天 2026-07-12 仅 12 天），由 `deepseek-v4-flash` / `deepseek-v4-pro` 取代。若现在硬编码旧名，M1 联调当天即断。

## 三、方案亮点（先肯定，避免无脑否定）

1. **上传即回任务 ID、重活走 Worker** —— 正确的异步拓扑，UI 不会卡死。
2. **解析（确定性）与理解（LLM）分离** —— 可单测、可重试、LLM 抽风不拖垮整条链路。
3. **向量粗排 + LLM 精排双引擎** —— 既快又可解释，还顺带给"如何优化简历匹配某岗位"留了口子。
4. **Docker Compose 一体化** —— 生产思维在线。

## 四、🔴 关键缺陷（M0 前必须修订）

### C1. 模型名硬编码 = 上线即崩
- **影响**：今天 2026-07-12，旧聊天模型 12 天后弃用。现在写死 `deepseek-chat`，M1 联调当天返回 404/模型不存在。
- **修复**：所有模型 ID 集中到配置（`LLM_CHAT_MODEL`、`LLM_EMBED_MODEL`）；默认用 `deepseek-v4-flash` / `deepseek-embedding`；加**启动健康检查 + 调用失败告警**；写一层 provider 抽象以便换模型/换厂商。

### C2. 延迟预算自相矛盾（<1.5s 物理上不可能）
- **影响**：原方案把"匹配 P95 <1.5s"写进质量目标，但匹配链路含 LLM 调用（结构化 + 匹配），单次即数秒到数十秒。1.5s 是我对*页面加载*的标准，被错误套用到 AI 流水线。
- **修复**：拆成两份预算——
  ① **接口/页面响应 <1.5s**（不含 AI 计算）；
  ② **简历处理为异步任务**，接受 10–60s，前端进度条/SSE。
  删掉"匹配 <1.5s"这条错误指标，改为"任务状态可查询、P95 完成时间有上界、接口层 <1.5s"。

### C3. 合规/隐私是生产级"门票"，原方案只字未落实
- **影响**：简历=敏感个人信息。原方案仅一句"加密与留存策略"，无机制。且把简历全文发给 DeepSeek 第三方云做结构化/匹配，对国内产品属"向第三方提供个人信息"，有 PIPL 合规考量。
- **修复（MVP 起就要有骨架）**：
  ① 静态加密（MinIO SSE / 磁盘加密）+ DB 字段脱敏；
  ② **最小化上送 LLM 的字段**（只送必要文本，不送身份证号等）；
  ③ 明确留存与删除（用户主动删除 + TTL 自动清理）；
  ④ 隐私/数据处理说明披露 AI 处理。即便 MVP 匿名，M1 也要把"删除按钮 + 自动清理"做进去。

### C4. OCR 是最贵最低频的格式，却和 MVP 强绑定
- **影响**：PaddleOCR 镜像 GB 级、需下载模型、容器多进程易踩坑；而图片简历在真实上传中占比最低。为它拖慢镜像构建、抬高 MVP 门槛不划算。
- **修复**：MVP 先支持 **PDF / Word / 文本**；OCR 作为**独立开关或后续里程碑**，或改用云 OCR（腾讯云 OCR 等）按需调用，避免自托管重资产。M1 不阻塞在 OCR 上。

### C5. 岗位库冷启动 = 匹配形同虚设
- **影响**：`jobs` 表为空时向量召回无结果，产品"看起来能用实则没用"。原方案只说"种子数据"，无规模/覆盖/来源策略。
- **修复**：M1 必须配套**结构化岗位种子**（建议 200–500 个跨职能角色，含 `required_skills` / `level` / `responsibilities`），脚本灌入并预计算嵌入；定义后续运营扩充与去重机制。否则匹配模块没有意义。

## 五、🟠 重要缺陷（会导致返工/质量事故）

### M1. LLM 结构化抽取对"真实脏简历"没有兜底
- 多栏排版、表格、中英混排、职业空窗、非标准标题、扫描件误判……仅靠"LLM + JSON schema + 置信度"太脆弱。
- **修复**：混合抽取——正则/字典抽取高精字段（邮箱、电话、年限、学历关键词、已知技能词表）+ LLM 补其余；检测"文本层为空 → 走 OCR"；schema 校验失败回退二次调用或人工复核队列；记录置信度用于展示。

### M2. Worker 框架未定（Celery vs ARQ）
- 两者差异大（Celery 需 broker+beat；ARQ 仅 Redis、async 原生、契合 FastAPI）。影响 Compose、监控、重试设计。
- **修复**：M0 前定 **ARQ**（Redis-only、async 友好），除非有强调度需求。

### M3. 缺质量评估（eval）体系
- "生产级匹配"无法证明好坏。无黄金集、无抽取准确率/匹配相关性自动化评估。
- **修复**：早期建小规模标注集（几十份简历 + 期望岗位/字段），持续跑抽取字段级准确率与匹配排序一致性。

## 六、🟡 中等（清晰度/一致性/可维护性）

- **M0 基础设施重于 MVP 需要**：6 容器（pg+pgvector / redis / minio / api / worker / web）对单人起步偏重。建议 dev 模式精简（SQLite+sqlite-vec 或仅 Postgres；本地磁盘代 MinIO；BackgroundTasks 代 Worker），把"生产 Compose"作为独立 profile，别第一天就上全栈。
- **结果推送契约未定**：前端如何得知匹配完成？轮询？SSE？需明确状态机（`uploaded → parsing → structured → matching → done/failed`）与查询接口/SSE 契约——这是核心 UX。
- **Monorepo 工具链未定**：pnpm workspaces？TS 类型与 Pydantic 如何不漂移（建议由 OpenAPI 生成客户端）？
- **匿名 MVP 无限流/配额**：DeepSeek 有速率与费用上限，单脚本可打爆预算。M1 起就要 per-IP 限流 + 全局 LLM 并发信号量。
- **上传安全偏浅**：魔数校验之外，缺大小强制、病毒扫描（Worker 内 ClamAV）、解压炸弹/加密 PDF 拒绝、解析超时。
- **M3 面试上下文管理**：长对话超上下文，需滚动窗口/周期摘要 + 成本上限。
- **M4 鉴权跨域**：NextAuth + web/api 双源 cookie/CSRF 需提前定边界（BFF 或 same-site）。
